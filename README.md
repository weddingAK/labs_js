# Lab 02: Objects, Prototypes, Classes & Entities

## Опис проекту

У рамках цієї лабораторної роботи проєкт розширено за рахунок введення об'єктно-оріентированого підходу (ООП). Реалізовано ієрархію на базі ES6-класів (`Entity` та `Ship`), векторну математику з чистими методами (`Vector2`), ігровий світ на основі `Map` для ефективного керування сутностями, систему колізій коло-коло, а також механіку стрільби з урахуванням концепції композиції.

## Розділ Reflection & Design Decisions

### 1. Виправлення проблеми з `this` у функції стрільби (`ship.fire`)

- **Проблема:** Якщо передати метод `ship.fire` безпосередньо у слухач подій (наприклад, `window.addEventListener('keydown', ship.fire)`), контекст `this` втрачається. Всередині методу `this` починає посилатися на глобальний об'єкт (`window`) або стає `undefined` у strict mode, що призводить до помилки звернення до властивостей корабля.
- **Рішення:** Для збереження правильного контексту `this` використовується стрілкова функція-обгортка (або анонімна функція у слухачі подій), яка викликає метод у контексті екземпляра: `() => ship.fire()`. Оскільки стрілкові функції не мають власного `this`, вони лексично успадковують його з навколишнього середовища.

### 2. Композиція проти глибокого дерева класів (Pickup & Homing)

- **Підхід:** Для реалізації додаткових особливостей гри (наприклад, бонусів-пікапів (`Pickup`) або самонаведення) свідомо обрано **композицію** замість розширення глибокої ієрархії класів (на кшталт `Entity -> MovingEntity -> Actor -> Item -> Pickup`).
- **Чому обрано композицію:** Глибоке наслідування у геймдеві швидко призводить до проблеми крихкої бази коду (_fragile base class problem_) та «вибуху класів». Завдяки композиції ми створюємо невеликі автономні класи-сутності та наділяємо їх необхідною поведінкою через модульні компоненти чи властивості, що робить архітектуру гнучкою та легко розширюваною.
